# 技術調査レポート — 要件定義の事実検証

**調査日**: 2026-07-18
**手法**: 5観点×並列Web調査 → 23ソース取得 → 110クレーム抽出 → 上位25件を3票制の敵対的検証(反証を試みる独立エージェント3体、2/3反証で棄却)。結果: **20件確認 / 4件棄却 / 1件検証未完**。検証未完・未検証のクレームは本文中で「参考(未検証)」と明示する。

**総合結論**: 要件定義書・アーキテクチャ設計の技術選定(シーンロールAPI、Core Imageパイプライン)は**一次情報で裏付けられた**。一方で、①Apple純正Multiportアダプタの1080p制限、②サーマルスロットリングの開始時間(十数分)、③超短焦点プロジェクター不適格、の3点は**要件定義書の記述を修正すべき新事実**であり、本レポートと同時に反映済み。

## 1. iPadOS外部ディスプレイAPI — 設計は正しい。追加の落とし穴あり

| 結論 | 確度 | 影響要件 |
|---|---|---|
| `UISceneSession.Role.windowExternalDisplayNonInteractive` は現行API(iOS/iPadOS 16.0導入、非推奨でない)。「外部接続ディスプレイに非インタラクティブなウィンドウを表示するシーン」と公式定義され、F-OUT-1の用途に合致 | 確認 3-0 [1] | F-OUT-1 |
| 旧ロール `windowExternalDisplay` およびInfo.plistキー `UIWindowSceneSessionRoleExternalDisplay` はiOS 16でdeprecated。使うべきは `UIWindowSceneSessionRoleExternalDisplayNonInteractive` | 確認 3-0 [1][2] | F-OUT-1(実装仕様) |
| SwiftUIのSceneライフサイクル単体では外部ディスプレイ用シーンを指定できず、カスタムAppDelegate+SceneDelegate(UIKitシーン管理)が必須。SwiftUIビューはUIHostingControllerでブリッジ可能 | 確認 3-0 [3][4] | 設計書§4(方針どおり) |
| `UIScreen.didConnectNotification` / `didDisconnectNotification` は非推奨。接続検出もシーンベースで行うこと(Apple Frameworksエンジニアの公式回答) | 参考(未検証) [5] | F-OUT-3 |
| **Stage Manager**: ユーザーが外部ディスプレイ上でアプリを起動すると、非インタラクティブシーンではなく通常の `windowApplication` シーン(インタラクティブ)が外部側に生成される。2経路の挙動差を考慮した設計・テストが必要 | 参考(未検証) [5] | F-OUT-1/F-OUT-3、リスクR5 |
| 落とし穴: QuickTime録画・キャプチャ系のミラーリング経路では外部シーンが生成されず、独立コンテンツではなくiPad画面がミラーされる。開発中の動作確認はHDMI実機で行うこと | 参考(未検証) [6] | M1スパイクの検証手順 |
| `UIApplicationDelegateAdaptor` 経由の状態共有は外部ディスプレイ用ビューでクラッシュする事例報告あり。iPad側UIと外部レンダラの状態共有はシングルトン等の明示的な共有機構で設計する | 参考(未検証) [4] | 設計書§2(ViewModel共有) |

**判定**: アーキテクチャ設計書§4の方針(UIKitシーン管理+映像専用VC)は正しい。Info.plistキー名・Stage Manager分岐・キャプチャ経路の注意を設計書に追記した。

## 2. リアルタイム映像処理性能 — 設計原則は裏付け済み、数値目標は実測必須

| 結論 | 確度 | 影響要件 |
|---|---|---|
| Core Image組み込みフィルタ(CIPerspectiveTransform含む)は全てMetal実装。ビデオアプリは組み込みフィルタ使用が最良性能というのがAppleの公式ガイダンス(WWDC20) | 確認 3-0 [7] | 設計書§1の技術選定 |
| 動画処理ではMTKView+CIRenderDestinationでテクスチャ返却ブロックを渡す方式が高性能(前フレーム完了を待たずにMetalワークをエンキュー可能) | 確認 3-0 [7] | 設計書§3.3 |
| CIContextは1つを再利用、`.cacheIntermediates: false`、他のMetal描画とはMTLCommandQueue共有、YUV(420f)ピクセルバッファを直接入力 — がAppleのベストプラクティス | 参考(WWDC20/公式ガイド由来) [7][8] | 設計書§3.3/§5 |
| AVPlayerItemVideoOutputによる毎フレームCVPixelBuffer取得はApple公式サンプルが実証する公認パターン。API自体はiOS 6から現行まで非deprecated | 確認 3-0 [9] | 設計書§3.3 |
| **ただし**: 「4K入力を3分割+3回射影変換+合成して30〜60fps」の定量的裏付けはどの一次ソースにも存在しない。Core Image性能は出力ピクセル数に比例するため、出力1080pなら達成が大幅に容易になる | 確認 3-0(文書の欠如として) [8] | N-PERF-1 → **M2冒頭に実測スパイク追加** |
| サーマルスロットリングは最新世代でも連続GPU高負荷の**9〜17分後**に開始する実測報告(M4: 約9〜15分、M5: 13〜17分)。「2時間連続投影」はスロットリング後の性能で成立させる必要がある | 参考(ゲーム負荷での実測、二次ソース) [10] | N-THERM-1(記述修正済み) |
| 注意: Apple公式サンプルAVBasicVideoOutputの描画部はCAEAGLLayer(OpenGL ES、現在deprecated)であり、そのまま流用不可。CADisplayLinkプル駆動はコミュニティ標準パターン([11]等)としては健在 | 棄却1件を反映 [9][11] | 設計書§3.3の出典整理 |

**判定**: パイプライン構造はApple公認パターンの組み合わせで妥当。ただし30/60fpsの数値目標は現時点で「仮説」であり、**M2の最初のタスクを「実機性能計測(1080p/4K出力別)」とする**。熱については「開始が十数分」を前提に段階的解像度低下(N-THERM-1)が必須機能であることが裏付けられた。

## 3. ハードウェア接続制約 — アダプタ選定が想定より重要

| 結論 | 確度 | 影響要件 |
|---|---|---|
| HDMI 2.0対応USB-C→HDMIアダプタ使用時: iPad Pro全機・Air(M2/M3/M4)・Air 5・mini(A17 Pro)・iPad(A16)は**4K60**出力可。**iPad Air 4・mini 6・iPad 10は4K30止まり** | 確認 3-0 [12] | N-COMP-1(機種マトリクス追加) |
| **Apple純正USB-C Digital AV Multiportアダプタは、ホーム画面とアプリ描画を1080p60に制限**する(Match Contentで4K60になるのは動画プレーヤー系コンテンツのみ)。CornerCastは「アプリが描画する映像」なので、純正Multiport経由では実質1080p出力になる可能性が高い | 確認 3-0 [12] | **新リスクR8**、N-COMP-1、F-OUT-5 |
| M4 iPad Proは外部1台に最大6K60をサポート。給電(Charging)とDisplayPort出力の同一ポート同時利用も公式仕様に明記 → 「給電しながらHDMI出力」はPD対応アダプタ/ドックで成立 | 確認 3-0 [13] | N-THERM-2(裏付け) |
| HDMI出力はUSB-CのネイティブDisplayPort出力+別売アダプタ経由が公式構成。HDMI→DVI/コンポジット等の再変換はApple公式に非互換。VGAは音声非伝送 | 確認 3-0 [13][14] | 推奨機材ガイド |
| AirPlay経由のマッピング出力は1〜3秒の遅延を伴うとの実務報告 | 参考(未検証、ブログ) [15] | F-OUT-6(警告文言の根拠) |
| everymacの「USB-C世代iPad Proは最大4K」という記述はAppleの一次情報(5K/6K対応)と矛盾し棄却。機種別上限はApple公式[12][13]のみを典拠とする | 棄却 1-2 [16] | — |

**判定**: **推奨アダプタの指定が要件級に重要**。「HDMI 2.0対応のUSB-C(DP Alt Mode)アダプタ+PDパススルー」を推奨構成とし、純正Multiportアダプタの1080p制限をリスクR8として追加した。M1実機スパイクで実際の出力解像度を必ず確認する。

## 4. 競合・類似アプリ — 「コーナー3面特化」の空白は確認

| 結論 | 確度 | 影響要件 |
|---|---|---|
| DynaMapperは「Optoma Projection Mapper」に改称済みで長期未更新。高ビットレート4Kでカクつき報告、矩形マッピング中心。旧レビューでは動画ソース非対応(静止画のみ)・$4.99 | 参考(未検証、ブログ2件) [17][18] | §1.1競合分析(修正済み) |
| 2026年の主要アプリリスト(SurfaBeam Pro, Optoma Projection Mapper, Lazy Lighting, HeavyM Remote, TouchViZ, ProMapper, Reality Augmenter等)に「部屋のコーナー3面特化」を謳う製品は存在しない。HeavyM RemoteはPC必須のリモコンでiPad単体完結ではない | 参考(未検証、ベンダー系記事) [17][15] | §1.1(ポジショニングの妥当性) |
| MadMapper(iOS/mini)の機能・価格は今回のソース群では一次確認できず。App Storeでの直接確認が残課題 | 未確認 | §1.1(残課題) |
| モバイル端末でのマッピングは「4K高フレームレート再生に不向き」との実務者評価があり、性能要件の警告材料 | 参考(未検証) [15] | N-PERF-1 |

**判定**: 「iPad単体完結×動画対応×コーナー3面特化」という組み合わせは既存製品にない、という要件定義の前提は現時点の情報で支持される。MadMapper iOS版のApp Store直接確認のみ残課題。

## 5. 物理的成立性 — 最重要の修正点。設置条件を要件に格上げ

| 結論 | 確度 | 影響要件 |
|---|---|---|
| **超短焦点(UST)プロジェクターは傾けて設置してはならず、傾斜時のフォーカス・輝度損失は補正不能**(VIOSO公式ワークフロー)。斜め投影が前提のCornerCastではUST機は**不適格** | 確認 3-0 [19] | **R1/R3の記述を修正**(旧版はUSTを推奨候補にしていた→誤り) |
| プロ向けイマーシブルームの標準構成は複数台(例: 床4×5m+壁2面で6台)。1台3面は業務標準から逸脱し、輝度・解像度・フォーカスの妥協が本質的に必要 | 棄却→ただし前段は事実 [19] ※「1台構成が不可能」との解釈は3票とも否定されず、「標準でない」ことのみ支持 | R2(表現強化) |
| 設置角度は20〜30度以内が推奨。30度超でフォーカス不均一(画面の一部のみ合焦)が発生。デジタル台形補正は画素を捨てるため実効解像度低下・ブラー・縁アーティファクトが必然 | 参考(未検証、ブログ) [20] | R4、設置ガイド(新規N-INST-1) |
| 没入壁面用途では短焦点(≠超短焦点)・3000〜3500ルーメン・投射距離1.5〜2.5mが推奨され、短い投射距離は観客の影の映り込みも減らす。通常投射比の機種は4〜8mを要し家庭の部屋では距離確保が困難 | 参考(未検証、ベンダー記事) [21] | 推奨機材ガイド(R1/R2対策) |
| 光学レンズシフト搭載機はデジタル補正と違い画質劣化なしで斜め投影できるが高価。ソフト補正のみのCornerCastは安価機材での画質低下が避けられない旨を明記すべき | 参考(未検証) [20] | R4 |
| 部屋の白い壁を直接スクリーンとして使う低コスト構成自体は業界でも認められた手法 | 参考(未検証) [22] | §1.2(前提の妥当性) |

**判定**: 「1台で3面」は業界標準外のトレードオフ込みの構成であり、**成立条件(設置角度・投射距離・機種タイプ)を非機能要件として明文化する必要がある**。要件定義書に設置要件N-INST-1を追加し、リスクR1〜R4を修正した。
