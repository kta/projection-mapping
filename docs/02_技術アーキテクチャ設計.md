# 技術アーキテクチャ設計書

要件定義書(`01_要件定義書.md`)の技術的裏付けとして、①クラス構成、②射影変換の実装ロジック、③外部ディスプレイ制御、④性能設計をまとめる。

---

## 1. 技術選定の結論

| レイヤ | 採用技術 | 理由 |
|---|---|---|
| UI | SwiftUI(+一部UIKitブリッジ) | 宣言的UIでコントロールポイント群の状態管理が簡潔。外部ディスプレイのシーン管理のみUIKitが必要 |
| 射影変換 | **Core Image(`CIPerspectiveTransform`)** | 4隅の座標を直接渡せばGPU上で正しいホモグラフィ変換を行う。行列計算・シェーダ実装が不要でMVPに最適。内部はMetalで実行されるため性能面も十分 |
| 動画デコード | AVFoundation(`AVPlayer` + `AVPlayerItemVideoOutput`) | 4K H.265のハードウェアデコード。フレームを`CVPixelBuffer`で取り出せる |
| 最終描画 | `CAMetalLayer` + `CIContext(mtlDevice:)` | Core Imageの結果を外部画面のMetalレイヤへゼロコピーで描画 |
| 永続化 | `Codable` + JSONファイル(Documents) | プリセットのエクスポート要件(F-PRESET-3)とスキーマが一致 |

**SceneKit/RealityKitは採用しない。** 本アプリの処理は「2D画像の切り抜き→平面ホモグラフィ→合成」であり、3Dシーングラフは過剰。将来ジャイロ連動(v2)を入れる場合も、ソース動画のクロップ位置をオフセットする2D処理で実現できる。

**なぜ2枚の三角形ポリゴンで変形しないのか(重要):** テクスチャ付き四角形を三角形2枚に割ってワープすると、対角線を境に補間が折れて画像が歪む(射影的に正しくないアフィン補間になる)。正しい結果には3×3ホモグラフィによる射影補間が必要で、`CIPerspectiveTransform` はこれを正しく行う。自前Metal実装に移行する場合も、頂点に同次座標(q値)を持たせた射影テクスチャリングが必須。


### 設計上のポイント

1. **状態源はViewModelの `MappingPreset` ただ一つ。** iPad側UIと外部ディスプレイのレンダラが同じ状態を観測することで「ツマミを動かすと投影が即変わる」を実現する。レンダラへは毎フレーム、値型スナップショット(`RenderParameters`)を渡す — 参照共有によるスレッド競合を構造的に排除する(N-PERF-2)。
2. **`FrameComposer` は純関数**(`compose(frame: CIImage, params: RenderParameters) -> CIImage`)。Core ImageのフィルタチェーンはCIImageのレシピ(遅延評価)を組み立てるだけで軽量なので、毎フレーム構築してよい。ユニットテストもしやすい。
3. **座標系は3つある**ことを明示的に扱う: ①UI座標(pt・左上原点)、②正規化座標(0–1・保存用)、③出力ピクセル座標(Core Image・左下原点)。変換は `CoordinateMapper` に集約し、散在させない。
4. Engine層はSwiftUI/UIKit非依存にし、M0(画面内MVP)→M1(外部出力)でそのまま流用する。

## 3. 射影変換の実装ロジック

### 3.1 概念

やりたいことは「矩形の映像を、任意の凸四角形へ写す」平面ホモグラフィ(射影変換)。3×3行列で表され、自由度8=4点の対応(x,y×4)で一意に決まる。だからUIは「4隅のツマミ」だけで完結する。

プロジェクターが斜めから投影して生じる台形歪みは、それ自体がひとつのホモグラフィ。アプリ側で**逆向きのホモグラフィ**をあらかじめ掛けておけば、壁面上では打ち消し合って正しい矩形に見える。ユーザーがツマミで指定するのは「出力キャンバス上のどの四角形に映像を押し込むか」であり、逆行列の計算はユーザーには見えない(そもそも `CIPerspectiveTransform` は目標4点を直接受け取るので、開発者も行列を意識しなくてよい)。

### 3.2 Core Imageでの実装(1面分)

```swift
import CoreImage.CIFilterBuiltins

func warp(_ source: CIImage, to quad: Quad, canvasSize: CGSize) -> CIImage {
    let f = CIFilter.perspectiveTransform()
    f.inputImage = source
    // Quadは正規化座標(左上原点)。Core Imageはピクセル座標(左下原点)なのでYを反転
    func ci(_ p: CGPoint) -> CGPoint {
        CGPoint(x: p.x * canvasSize.width, y: (1 - p.y) * canvasSize.height)
    }
    f.topLeft     = ci(quad.topLeft)
    f.topRight    = ci(quad.topRight)
    f.bottomLeft  = ci(quad.bottomLeft)
    f.bottomRight = ci(quad.bottomRight)
    return f.outputImage ?? source
}
```

3面の合成は `source.cropped(to:)` で切り出した3枚をそれぞれ `warp` し、黒背景に `composited(over:)` を2回重ねるだけ:

```swift
func compose(frame: CIImage, params: RenderParameters) -> CIImage {
    let black = CIImage(color: .black).cropped(to: CGRect(origin: .zero, size: params.canvasSize))
    return params.orderedSurfaces  // 床→左壁→正面壁 の順
        .reduce(black) { canvas, s in
            let cropped = frame.cropped(to: s.cropRectInPixels(frame.extent))
                               .transformed(by: .init(translationX: -s.cropOriginX, y: -s.cropOriginY))
            return warp(cropped, to: s.quad, canvasSize: params.canvasSize)
                .composited(over: canvas)
        }
}
```

ここまで**シェーダを1行も書かずに**要件のコア(3分割→射影変換→再統合)が成立する。これがCore Image採用の最大の理由。

### 3.3 動画への適用と描画ループ

```swift
// セットアップ(1回)
let output = AVPlayerItemVideoOutput(pixelBufferAttributes: [
    // YUV(420f)のままCore Imageに渡す — RGBA変換コストを回避(Apple公式ガイド)
    kCVPixelBufferPixelFormatTypeKey as String: kCVPixelFormatType_420YpCbCr8BiPlanarFullRange
])
playerItem.add(output)
// CIContextは1つを生成して使い回す(毎フレーム生成は禁止)。
// 動画は毎フレーム内容が変わるので中間キャッシュは無効化する(WWDC20-10008)。
let ciContext = CIContext(mtlDevice: MTLCreateSystemDefaultDevice()!,
                          options: [.cacheIntermediates: false])

// 外部ディスプレイのCADisplayLinkから毎フレーム呼ばれる
func renderTick(_ link: CADisplayLink) {
    let t = output.itemTime(forHostTime: link.targetTimestamp)
    guard output.hasNewPixelBuffer(forItemTime: t),
          let pb = output.copyPixelBuffer(forItemTime: t, itemTimeForDisplay: nil),
          let drawable = metalLayer.nextDrawable() else { return }
    let composed = composer.compose(frame: CIImage(cvPixelBuffer: pb),
                                    params: currentParams)  // ViewModelのスナップショット
    ciContext.render(composed, to: drawable.texture, commandBuffer: nil,
                     bounds: composed.extent, colorSpace: CGColorSpaceCreateDeviceRGB())
    drawable.present()
}
```

- デコード(AVPlayer・HW)→ CIフィルタ(GPU)→ Metal描画まで**ピクセルがCPUに降りてこない**構成。CPU⇔GPUの往復コピーは4K/BGRAで1フレーム約33MBに達し、入れた時点で破綻する。
- Core Imageの処理コストは**出力ピクセル数に比例**する(Apple公式ガイド)。出力先が1080pなら中間処理も1080pで行う — 4K60が未達の場合の第一の逃げ道はここ。
- 自前のMetal描画と併用する場合はCIContextを**同一のMTLCommandQueue**で生成し、GPUのwaitバブルを避ける(WWDC20-10008)。より高性能な形として、MTKView+`CIRenderDestination`(テクスチャ返却ブロック方式)は前フレーム完了を待たずに次フレームのエンキューを開始できる。
- 明るさ/ガンマ(F-WARP-6)は各面のwarp前に `CIColorControls` / `CIGammaAdjust` を挟むだけ。
- 静止画(F-SRC-2)は `CIImage(contentsOf:)` を同じ `compose` に流すだけで共通化できる。
- **性能の数値目標(30/60fps)は文献上の裏付けが存在しない仮説**であり、M2冒頭の実機計測スパイクで確定させる(調査レポート§2)。CADisplayLinkプル駆動+AVPlayerItemVideoOutputはコミュニティ標準パターンだが、Apple公式サンプル(AVBasicVideoOutput)は描画部がOpenGL ESの旧世代実装なのでそのまま流用しないこと。

### 3.4 事前レンダリング(ベイク)モードの実装

リアルタイムモードと**同じ `FrameComposer.compose` をオフラインで回すだけ**にする — 2系統のワープ実装を持たないことが正しさの担保になる(ベイク結果とリアルタイム表示が必ず一致する)。

```swift
// 書き出し: AVVideoComposition のCIフィルタ適用イニシャライザが
// 「毎フレームCIImageを受け取り、加工結果を返す」形でFrameComposerをそのまま差し込める
let composition = AVMutableVideoComposition(asset: asset) { request in
    let composed = composer.compose(frame: request.sourceImage, params: bakeParams)
    request.finish(with: composed, context: sharedCIContext)
}
composition.renderSize = params.canvasSize   // 出力解像度(1080p/4K)をここで確定

let export = AVAssetExportSession(asset: asset, presetName: AVAssetExportPresetHEVCHighestQuality)!
export.videoComposition = composition
export.outputFileType = .mp4
export.outputURL = bakeStore.url(for: preset)
await export.export()                        // 進捗は export.progress を監視
```

- 音声トラックは `AVAssetExportSession` がそのままコピーする(F-BAKE-1)。
- `BakeStore` はベイク動画のメタデータ(生成元プリセットのハッシュ・生成日時・解像度)をJSONで保持し、プリセット変更検知(F-BAKE-3)はハッシュ比較で行う。
- **ベイク再生モードのレンダラは存在しない**: 外部ディスプレイの `UIViewController` に `AVPlayerLayer` を張って再生するだけ。CIContext・CADisplayLinkは不要で、GPU負荷はHWデコードのみ(N-THERM-1の根本対策)。
- 書き出し所要時間はソース長・解像度に依存する(4K/H.265の再エンコードは実時間の数倍かかり得る)。進捗UI(F-BAKE-4)は必須。
- 同じ `AVVideoComposition` は `AVPlayerItem.videoComposition` に設定すればプレビュー再生にも使えるため、「ベイク前に結果を確認」機能も追加コストほぼゼロで実現できる。

### 3.5 将来Metal直書きへ移行する判断基準

Core Imageで性能要件(N-PERF-1)を満たせる見込みが高いためv1はCore Imageで通す。以下のいずれかが必要になった時点で `FrameRenderer` プロトコルの別実装としてMetal版を追加する:
- 多点グリッドワープ(床の非平面対応・v2)
- フレームごとの視差オフセット+モーションブラー等の演出(ジャイロ連動・v2)

## 4. 外部ディスプレイ制御(Non-Interactiveモード)

iPadOSでは外部ディスプレイはデフォルトでミラーリングになる。独立コンテンツを出すには**シーンベースのライフサイクル管理**が必要で、ここだけはUIKitを使う(SwiftUIのSceneライフサイクル単体では外部ディスプレイ用シーンを宣言できないことが調査で確認済み — 調査レポート§1):

1. `Info.plist` でマルチシーンを有効化(`UIApplicationSupportsMultipleScenes = YES`)し、Application Scene Manifestに **`UIWindowSceneSessionRoleExternalDisplayNonInteractive`** のシーン構成を宣言する。※旧キー `UIWindowSceneSessionRoleExternalDisplay` はiOS 16でdeprecated — 使わない。
2. `UIApplicationDelegate.application(_:configurationForConnecting:options:)` で、接続シーンの `session.role == .windowExternalDisplayNonInteractive` を判定し、外部用の `UISceneConfiguration` を返す。接続/切断検出もシーンベースで行う(`UIScreen.didConnectNotification` はdeprecated)。
3. 外部シーンの `SceneDelegate` で `UIWindow(windowScene:)` を生成し、ルートに **`CAMetalLayer` を持つだけの `UIViewController`** を置く(SwiftUIビューは載せない — F-OUT-2)。このロールのシーンは名前どおり非インタラクティブ(外部側でのタッチ操作は不可)。
4. `sceneDidDisconnect` で `OutputRenderer` を停止し、ViewModelの `displayState` を更新(F-OUT-3)。
5. `windowScene.screen` の `currentMode` から出力解像度を取得し、レンダリングキャンバスサイズに反映(F-OUT-5)。

SwiftUIアプリ本体とは `@main` の `App` に `@UIApplicationDelegateAdaptor` を付けて共存させる。

**調査で判明した落とし穴**(いずれもM1実機スパイクの検証項目。リスクR5/R8):
- **Stage Manager**: ユーザーが外部ディスプレイ上でアプリを起動すると、非インタラクティブシーンではなく通常の `windowApplication` シーン(インタラクティブ)が外部側に生成される経路がある。両経路でロールを判定し、意図しない側にUIが出ないようにする。
- **状態共有**: `@UIApplicationDelegateAdaptor` 経由の環境オブジェクト共有は外部ディスプレイ用シーンでクラッシュする事例報告がある。iPad側UIと外部レンダラの共有状態(`MappingViewModel`)は明示的なシングルトン/依存注入で渡す(§2の設計はこれに対応済み)。
- **キャプチャ経路**: QuickTime録画などのミラーリング/キャプチャでは外部シーンが生成されず、独立コンテンツを確認できない。動作確認は必ずHDMI実機で行う。
- **アダプタ**: Apple純正Multiportアダプタはアプリ描画を1080pに制限する(要件定義書R8)。スパイクではHDMI 2.0対応サードパーティアダプタと比較し、`screen.currentMode` の実値を記録する。

## 5. 性能・熱設計の要点

| 項目 | 設計 |
|---|---|
| フレーム駆動 | 外部画面の `CADisplayLink`(接続先Hzに同期)。iPad側プレビューは30fpsに間引き可 |
| スレッド | UI=MainActor / レンダリング=専用スレッド(DisplayLink)。受け渡しは値型スナップショットのみ |
| 熱制御 | `ProcessInfo.thermalState` 監視。`serious` でレンダリング解像度を75%→50%に段階降格(N-THERM-1) |
| 電源 | `UIApplication.shared.isIdleTimerDisabled = true`(投影中のみ) |
| 計測 | MetalのGPUフレーム時間+`CADisplayLink` のスキップ数をデバッグHUDに表示(開発ビルドのみ) |
