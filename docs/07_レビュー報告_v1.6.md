## 総評

要件定義書 (docs/01) の Must 機能はほぼ全て「コードとして書かれている」段階まで到達しており、12点キャリブレーション・区分的ホモグラフィ・ベイク書き出し・プリセット永続化・OSC/MIDI といったプロ機能まで一通り揃っている。座標変換を `CoordinateMapper` 1箇所に集約する規約や、プレビューと出力で同じ `FrameComposer` を通す設計は、この種のアプリで最も壊れやすい部分を正しく押さえている。

一方で、**「プロジェクターに繋いだ、リアルタイム、動画」という単一の主経路の外に出た途端に静かに壊れる**箇所が集中している。再生パイプラインが `ExternalDisplayManager` に完全に閉じ込められているため未接続時とベイク再生中はトランスポートが死に、出力モードとコンテンツ種別の整合を取る主体が存在しないため「ベイク再生モードのまま別の動画を選ぶ」と前の映像が投影され続ける。編集ロックにも素通しの経路が複数ある。いずれもクラッシュやデータ損失を伴わず、**無言で誤った状態を維持する**のが共通の性質で、ユーザーからは原因が分からない。

blocker 相当は無い。high 4件を潰せば「他人に触らせられる」水準になる。残りは精度・一貫性・保守性の問題。

## サンプルは動くか

### 確定した事実 (ffmpeg / numpy による実測)

**アセット実体** — 3本とも存在し、破損なし。
`warp-drive.mp4` (1,992,169 B) / `gentle-ocean.mp4` (1,419,756 B) / `firefly-forest.mp4` (761,535 B)。
全て 1920x1080 / h264 High / yuv420p / 30fps / 12.00秒 / 360フレーム、全フレームデコード成功。**音声トラックは無し**(トランスポートの音量スライダは同梱サンプルに対しては効く相手がいない)。

**バンドル同梱経路** — 静的には成立している。`project.yml` の target は `sources: [CornerCast]` のみで type 指定が無く、XcodeGen は既知拡張子以外を既定で `.resources` ビルドフェーズに入れる。フォルダ参照ではないためバンドル直下にフラットに置かれ、`SampleVideos.swift:15-17` の `Bundle.main.url(forResource: id, withExtension: "mp4")` で解決できる。ID (`warp-drive`/`gentle-ocean`/`firefly-forest`) と実ファイル名・拡張子は一致。`CornerCast/` 配下の非 Swift ファイルは `Info.plist` と mp4 3本だけで、意図しない混入も無い。**ただしこれは XcodeGen のソースコードとリポジトリ構成からの推論であり、実際に生成された .app の中身は確認していない。**

**構図とデフォルトクロップの一致** — 一致している。`tools/make_samples.py:11-14` のゾーン定義 (左壁 x0-640/y0-756、正面壁 x640-1280/y0-756、床 x640-1280/y756-1080) は、`Models.swift:359-372` の `makeDefault()` の crop (左1/3×上70%、中央1/3×上70%、中央1/3×下30%) を `CoordinateMapper.ciRect` の Y 反転規則で解いた結果と一致する。

**各面に絵が来ているか** — 全360フレームを実測した(輝度 gray、0-255)。

| warp-drive | mean 3.4 / >60画素 0.16% | mean 9.3 / 0.30% | mean 4.2 / 0.23% |
| gentle-ocean | mean 138.0 / 100% | mean 160.1 / 100% | mean 76.9 / 84.7% |

3本×3ゾーンの全てで「輝度60超の画素が1つも無いフレーム」は 360 フレーム中 0 件。**どの面も常に何かが映る**という設計意図は満たされている。ただし `warp-drive` と `firefly-forest` は全体が非常に暗い素材で、平均輝度が一桁〜20台。明るい部屋では投影が見えない可能性がある(これは実機でしか判断できない)。

### 確定した問題

**再生経路が繋がっていない。** サンプルを選んでも、**プロジェクターを繋いでいなければ1フレームも動かない**。`VideoSource` の生成箇所はリポジトリ全体で `ExternalDisplayManager.swift:189` の1箇所だけで、外部シーン接続からしか到達しない。未接続時の iPad 内プレビューは `EditorPreviewRenderer.swift:77-85` が `AVAssetImageGenerator.copyCGImage(at: .zero)` で取った先頭1フレームを URL 単位でキャッシュして返すだけ。詳細は「直すべきこと #1」。

**ベイク再生モードのままサンプルを選ぶと切り替わらない。** 詳細は「直すべきこと #2」。

### 未検証の限界

**iPad 実機・Mac Catalyst・実プロジェクターでの確認は一切していない。** したがって以下は不明のまま:
- そもそもビルドが通るか(Xcode が無く、型チェックすらしていない)
- 実際に .app にサンプル mp4 が入るか
- 3面同時合成が 30/60fps を維持できるか(docs/04:36 が「性能目標は現時点で仮説」と自認している)
- 実投影での明るさ・色・サーマル降格の挙動
- Metal 描画とプレビュー描画の見た目の一致

### #1 (high) 再生パイプラインが外部ディスプレイに全依存している

**場所**: `CornerCast/UI/TransportView.swift:36`, `:205` / `CornerCast/Scenes/ExternalDisplayManager.swift:159,189,194` / `CornerCast/UI/EditorPreviewRenderer.swift:77`

**何が起きるか**

トランスポートの全操作は `viewModel.activeVideoSource` に委譲されるが、この参照に非 nil を代入するのは `ExternalDisplayManager.makeRealtimeSource` の `case .video` 分岐だけ。したがって (a) 外部ディスプレイ未接続時は常に nil、(b) 接続中でも `outputMode == .bakedPlayback` のときは `reconfigure()` 冒頭 (`:159`) で nil に戻され、以後 `makeRealtimeSource` を通らないため nil のまま。

さらに悪いのは状態表示が嘘をつくこと。再生ボタンは

```swift
Button { isPlaying.toggle(); if isPlaying { viewModel.activeVideoSource?.play() } ... }
```

と `isPlaying` を**先に**トグルしてから nil に委譲し、状態を戻すはずの `syncPlaybackUI()` は

```swift
guard let player = viewModel.activeVideoSource?.player else { return }   // :205
```

で `isPlaying` の更新前に return する。結果、アイコンは `pause.fill` に変わったまま固定され、UI は「再生中」と言い続ける。音量 `onChange` (`:74-76`) とシーク (`:196-201`) も同じ optional で行き止まり。ベイク再生の `queue.volume` は `startBakedPlayback` 時の1回しか設定されない (`:216`)。MIDI/OSC 側 (`ControlHub.swift:153,156,198,199`) も同じ穴を通る。

同時に、未接続時の iPad 内プレビューは動画に対して先頭1フレームの静止画しか返さない (`EditorPreviewRenderer.swift:77-85`、コメント自身が「プレビューは静止でよい」と明記)。再描画トリガも `MeshCanvasView.swift:80` の `.task(id: previewKey)` のみで、`previewKey` は `calibrationFingerprint + contentKey` (時間項ゼロ)。UI 側に TimelineView も CADisplayLink も存在しない。

**ユーザーから見た症状**: プロジェクターを持たない人が起動 → サンプル「ワープ航行」を選択 → 暗い静止画が1枚出るだけ → 再生ボタンを押す → アイコンだけ一時停止に変わり、絵もシークバーも一切動かない。壊れているのか操作を間違えたのか判別できない。ベイク再生モード(長時間投影の既定モード、docs/01:145)では外部ディスプレイに繋いでいても一時停止も音量調整もできない。

**要件との関係**: F-OUT-4 (M, docs/01:93「未接続時は…出力相当の映像を表示する」) の部分未達。F-SRC-4 (S, docs/01:104) の機能不全。docs/02:211 は「iPad側プレビューは30fpsに間引き可」と書いており、実装は設計より後退している。

**直し方**
1. `VideoSource` の生成責務を `ExternalDisplayManager` から `MappingViewModel`(または新設の `PlaybackCoordinator`)へ移し、外部接続の有無に関わらず `activeVideoSource` が常に生きるようにする。外部接続時はその同一インスタンスを `OutputRenderer.source` に差す。これで F-OUT-4 / F-SRC-4 が接続状態に依存しなくなる。
2. ベイク再生用の `AVQueuePlayer` も同じ抽象 (play/pause/seek/volume) で公開し、TransportView に結線する。最低限 `preset.volume` の変更に `bakedPlayer.volume` を追随させる。
3. 再生状態は必ず実プレイヤーから導出する。`isPlaying` を先にトグルしない。
4. プレビューは `AVPlayerItemVideoOutput` を持たせて 15〜30fps で `compose` を回す。負荷が問題なら静止のままでよいが、その場合は「未接続のため先頭フレームを表示しています」と画面に明示し、無反応なコントロールは `.disabled` にして理由を1行添える(無言の無効化にしない)。

### #2 (high) 出力モードとコンテンツ種別を整合させる主体がいない

**場所**: `CornerCast/Scenes/ExternalDisplayManager.swift:162-167` (真の原因行) / `:202-207` / `CornerCast/UI/ContentPickerView.swift:101,140`

**何が起きるか**

`reconfigure()` の分岐は `.realtime` 側にだけ `stopBakedPlayback()` があり、`.bakedPlayback` 側には無い:

```swift
case .bakedPlayback:
    renderer?.stop(); renderer?.source = nil
    startBakedPlayback()          // ← stopBakedPlayback() が無い
case .realtime:
    stopBakedPlayback()
```

そして `startBakedPlayback()` は `host?.setMode(.bakedPlayback)` を実行した**後**に `guard case let .bakedVideo(url) = viewModel.contentSource else { return }` で早期 return する。コメントは「黒画面のまま待機」と書いているが、`bakedPlayer` / `bakedLooper` / `host.playerLayer.player` は解放されないため、実際には**前のベイク動画がループ再生を続ける**(コメントが実挙動と矛盾している)。

一方 `outputMode` を `.realtime` に戻す経路は、`EditorView.swift:106` のモード Picker と `ControlHub.swift:161` の OSC しか無い。コンテンツ選択の全導線(サンプル `:101`、PhotosPicker `:176/:198`、fileImporter `:230/:232`、テストパターン `:33`)は `contentSource` しか書かない。`MappingViewModel` の `outputMode`(`:23`)と `contentSource`(`:32`)はどちらも `didSet` を持たない素の格納プロパティで、整合を取るロジックがどこにも無い。

**ユーザーから見た症状**: ベイク書き出し完了 →「ベイク再生に切替」→ 数分後に別の映像を試そうとコンテンツ選択から「ホタルの森」をタップ → プロジェクターには前のベイク動画が流れ続け、iPad の UI だけが「ホタルの森を選択済み」になる。エラーもトーストも出ない。エディタ上部のモード Picker に気づかない限り復帰できず、**かんたんセットアップ (`SimpleSetupView`) にはモード切替 UI が存在しないため、この画面からは復帰手段がゼロ**。逆に `.realtime` × `.bakedVideo` の組み合わせでは `makeRealtimeSource` が nil を返し、`OutputRenderer` の `lastFrame` 保持により古いフレームが凍結表示される。

**要件との関係**: F-MODE-1 (M, docs/01:143) / F-BAKE-2 (M, docs/01:145) の機能不全。

**緩和材料**: `outputMode` は `MappingPreset` に含まれず永続化されないため、再起動すれば `.realtime` に戻る。恒久的な破損ではない。

**直し方**
1. `reconfigure()` の `.bakedPlayback` 分岐の先頭で必ず `stopBakedPlayback()` を呼ぶ(または `startBakedPlayback()` 冒頭で既存プレイヤーを停止する)。
2. `MappingViewModel` に `func selectContent(_ source: ContentSource)` を用意し、`.bakedVideo` なら `.bakedPlayback`、それ以外なら `.realtime` に `outputMode` を揃える一元的な入口を作って、UI からの直接代入を廃止する。
3. 防御的に `reconfigure()` 側でも `case .bakedPlayback where !isBakedVideo(contentSource)` を `.realtime` へフォールバックさせる。
4. `startBakedPlayback()` の「黒画面のまま待機」の無言 return はやめ、理由を viewModel 経由で UI に出す。コメントも実挙動に合わせて訂正する。

### #3 (high) 編集ロックが複数経路で素通しになる

**場所**: `CornerCast/UI/InspectorView.swift:217` (resetSection), `:268-287` (色スライダの Binding), `:37-47` (座標 TextField), `:202-213` (linkSection), `:138-143` (自由面スライダ) / `CornerCast/State/MappingViewModel.swift:345,352,330,216`

**何が起きるか**

F-UI-6 (docs/01:162「調整完了後、誤タッチで動かないようにする」) の編集ロックは `MeshCanvasView` の `allowsHitTesting` と一部ボタンの `.disabled` にしか効いていない。ガードの有無が一貫していない:

- `resetAll()` / `resetSurface()` (`MappingViewModel.swift:345,352`) に `guard !isEditLocked` が無く、`InspectorView.swift:233-237` の「全てリセット」ボタンにも `.disabled` が無い。**ロック中に赤いボタン1タップで12点が初期値に戻る。**
- 明るさ/ガンマ/エッジぼかしの Binding は `set: { viewModel.preset.surfaces[s]?.brightness = $0 }` と ViewModel を経由せず preset を直接書くため、ロックを完全に無視する。
- `setLink(id:enabled:)` (`:330`) にガードが無く、Toggle も disabled されていない。有効化すると b 側頂点が a 側位置へ吸着するので、**ロック中に頂点座標そのものが動く**。
- `updateExtra` (`:216`) にもガードが無く、自由面の色調整と名前変更が素通しする。
- 逆に座標 TextField は disabled されていないのに `move()` が弾くため、入力しても値が戻るだけで理由が表示されない。しかも `coordBinding` の set が呼ぶ `beginGesture()` = `pushUndo()` はガードの外にあるため、**ロック中の無効な入力でアンドゥスタックだけが積まれ、既存の履歴が上限20から押し出される**。

同じファイル内に `.disabled(viewModel.isEditLocked)` が6箇所 (`:71,118,132,147,181,192`) 存在することが、付け忘れであることを裏付けている。`InspectorView` は `EditorView.swift:31` で常時 280pt 固定配置されており、ロック中も到達可能でなければならない(ロックトグル自体が resetSection にある)。

**ユーザーから見た症状**: 本番前にロックを ON にして iPad を客席に置く → 誰かがインスペクタ最下部の赤い「全てリセット」に触れる → ロックしているのに投影が崩壊する。逆に明るさスライダだけはなぜか動く。ロックが何を守るのかユーザーから予測できない。

**緩和材料**: `resetAll`/`resetSurface` は `pushUndo()` を通るため「元に戻す」1回で復帰できる。ただし誰かが気づいた場合に限られ、`preset` の `didSet` → `scheduleAutosave` で 500ms 後にはディスクにも保存される。

**直し方**: リセット・色調整・リンク・自由面更新をすべて `guard !isEditLocked` 付きの ViewModel ミューテータ経由にし、UI 側も `.disabled(viewModel.isEditLocked)` を全操作へ一貫適用する。ガードで弾く場合は `pushUndo()` より前に return する。ロック中はセクション先頭に「編集ロック中です」と無効化の理由を表示する。

### #4 (high) `preferredTransform` が実出力パスだけ未適用

**場所**: `CornerCast/Engine/VideoSource.swift:74` (`return CIImage(cvPixelBuffer: pixelBuffer)`) / `CornerCast/UI/EditorPreviewRenderer.swift:80` (`generator.appliesPreferredTrackTransform = true`)

**何が起きるか**

リアルタイム出力の `VideoSource.copyFrame` は `CVPixelBuffer` を `CIImage` に包むだけで、動画トラックの `preferredTransform` を適用しない。一方エディタプレビューの `posterFrame` は `appliesPreferredTrackTransform = true` を設定して向き補正済みの絵を出す。`grep` の結果、`preferredTransform` / `appliesPreferredTrackTransform` / `oriented(` / `applyOrientationProperty` のヒットは前者1件のみ。

crop は正規化矩形なので、向きが90度違えば**各面に割り当てられるソース領域が完全に別の場所になる**。縦撮り素材ではプレビューが 1080×1920、実バッファが 1920×1080 と extent 自体が異なる。

決定的なのは `EditorPreviewRenderer.swift:5-7` のコメントが「プレビューと実際の投影結果が必ず一致することを構造的に保証する」と宣言していること。ソースフレーム取得だけが別経路になっていて、この不変条件が破れている。

**ユーザーから見た症状**: iPhone で縦に撮った動画を読み込むと、エディタでは正立した映像でクロップ枠と3面が見えるのに、プロジェクターには90度倒れた映像が出る。左壁には正立時なら床にあたる帯が投影される。

### #6 (medium) メッシュのセル境界に暗いシームが出る

**場所**: `CornerCast/Engine/FrameComposer.swift:119` (`acc = out.composited(over: acc)`)

`meshWarped` は (rows-1)×(cols-1) のセルを1枚ずつ `CIPerspectiveTransform` して順に source-over 合成する。各セルの射影変換結果は境界でアンチエイリアスされ、辺上のアルファが1未満になる。隣接セルは同じ制御点を共有するので、同じ境界線上で相補的な傾斜どうしが合成され、合成後アルファは `1 - αL·αR` にしかならない。**最悪 0.75 (25%暗化)、DOD が厳密にクリップされる場合は 0.50 (50%暗化)。** 4×4 メッシュなら内部境界は縦2本・横2本の計4本。

`:105-107` の `cropped(to: srcRect)` は `CoordinateMapper.ciRect` で丸めも膨張もせず厳密分割するため、幾何的には隙間も重複も無く、アルファだけが不足する典型的な conflation artifact の条件が揃っている。`:90-91` のコメント「隣接セルは制御点を共有するため、境界は連続する / フェザーは分割前に適用済みなので、セル境界に切れ目は出ない」は**事実に反する**(フェザーは `warpedPiece` で面の外周にしか掛からない)。まずこのコメントの訂正が必要。

**何が起きるか**: メッシュを ON にすると映像の中に等間隔の暗い格子線が現れる。制御点を動かしても消えず、暗い場面ほど目立つ。ユーザーには「メッシュを入れると画質が落ちる」としか見えない。

**直し方**: (a) 応急処置として `srcRect` と宛先 quad を半〜1ピクセル分だけ外側へ広げて重ね代を作り、隣接セルのアンチエイリアス帯を互いに埋める。(b) 本筋は `CIMeshGenerator` か自前 `CIWarpKernel`(逆写像で最寄りセルのホモグラフィを引く単一カーネル)に置き換え、面全体を1パスで描いてセル境界を無くす。

**確度の注記**: `CIPerspectiveTransform` がソース空間でバイリニアサンプリングし DOD 外を透明黒とする、という前提は `CIWarpKernel` の仕様からの推論であり、Core Image を実行して画素を確認したわけではない。既存テスト (`ProFeatureTests.swift:123-172`) も extent しか見ていないので、**実機での目視確認が必要**。

## 確認したが問題なかったこと

以下は不安になりやすい箇所だが、追跡・実測した結果、欠陥ではなかった。

- **プリセット読込で未保存の調整が失われるか** — 失われない。`preset` への代入は `undoStack` をクリアしないため、読込後に「元に戻す」で直前の状態へ戻せる。undo セマンティクスを Python で再実装して誤タップシナリオを流し、`canUndo = True` / 1回で直前 / 2回でその前、を確認した。失うのは最後の微調整1回分のみ。
- **正面壁と床の頂点が重なって掴めなくなるか** — 既定配置では起きない。既定の y 差 0.05 は 12.9インチ横向きで約30.5pt、当たり円半径は22pt なので中心は円の外にある。完全一致させた場合も、上位 z の点をタップで選んで数値入力/十字キーで退避させる、頂点リンク (F-WARP-5) を有効化して1点として扱う、メッシュを有効化してハンドルの z を上げる、といった復帰路が複数ある。
- **退化した四角形で NaN/Inf が出てクラッシュするか** — アプリ側は自分で逆行列を解いておらず (`invert`/`inverse`/`determinant`/`simd`/`matrix` は全て0ヒット)、CIFilter の出力は全て `??` でガード、`compose` は末尾で必ず有限の `canvasRect` に `.cropped` する。Swift の Double は NaN でトラップしない。座標は `Quad.clamped` で常に有限な 0-1 に留まるためプリセット JSON に NaN が焼き付くこともない。F-WARP-4 (docs/01:124) は「結果が乱れるのは許容」と明記しており、要求はクラッシュ・フリーズしないことだけ。
- **`NSLocalNetworkUsageDescription` が無くて OSC が OS に遮断されるか** — されない。このコードベースは `NWListener` で受けるだけで、`NWConnection` の能動生成も `send` も0件、Bonjour 広告もブラウズも無い。Apple の公式見解では受信専用リスナー(UDP 含む)はローカルネットワークプライバシーの対象外。将来 OSC フィードバック送信や自動発見を足すときには必要になる。
- **エディタキャンバスの 16:9 固定で非 16:9 プロジェクタの継ぎ目がずれるか** — ずれない。`ciPixel` は各軸独立の異方スケールで、アフィン変換なので直線は直線のまま、共有頂点は出力ピクセル上で完全に一致する。sample プリセットで数値検証したところ、canvas を 1920x1200 / 1024x768 に変えても継ぎ目頂点のズレは 1e-13px オーダー。残るのは見かけの縦横比の違いだけ。
- **クロップ編集の非等方プレビューで選択領域がずれるか** — ずれない。画像と crop 矩形が同一の非等方写像を受けるので、囲むソース画素集合は不変。4:3 素材で実測して mean abs diff = 0.0 / corr = 1.0 を確認した。むしろ背景だけアスペクトフィットにすると本物の位置ズレを作る。
- **`warp-drive` の左壁/床が真っ黒で2面に何も映らないか** — 映る。全360フレームで輝度60超の画素が0個のフレームは3ゾーンとも0件(上表)。暗いのは素材全体であって、特定のゾーンだけが欠けているわけではない。
- **「サンプル」テンプレートが同梱動画を使わずテストパターンを出すこと** — 仕様どおり。`Models.swift:288` が `case sample // サンプル(調整済みデモ+テストパターン)` と明記し、`ProFeatureTests.swift:267-273` が契約としてテストで固定している。「調整済み」は `make(template: .sample)` が入れるパース付き quad を指す。F-SRC-7 は同梱サンプルの導線をコンテンツ選択シートと定めており、実装はそのとおり。
- **4K 合成がメインスレッドで走ることによる UI 競合** — 構造的に崩れているとは言えない。`link.add(to: .main, forMode: .common)` の `.common` はドラッグ追従中も投影を止めないための指定。`FrameComposer.compose` は CIImage の遅延グラフを組むだけで、`ciContext.render(_:to:commandBuffer:...)` は非同期版でGPU完了を待たない。3面はキャンバス内の重ならない部分矩形で「4Kを3回」ではない。ただし `ExternalDisplayManager.swift:39-41` のコメントが「バックグラウンドの CADisplayLink スレッド」と書いているのは事実と食い違うので訂正すべき(結果として `OSAllocatedUnfairLock` は冗長だが無害)。**実測は実機でしかできない**。docs/04:36 も性能目標を「仮説」と宣言している。
- **ベイクの「再書き出し推奨」バッジが行き止まりか** — 行き止まりではない。「コンテンツ」ツールバーは常時押せ、そこで元の動画を選び直せば書き出しボタンが有効化される(3タップ)。`HelpView.swift:47-50` にも同じ手順が書かれている。ただし `isStaleBakeExists` が presetID で絞らず全レコードを走査するためバッジがノイジー、再書き出しが毎回新規 UUID を作るため古い stale レコードが残りバッジが消えない、という別の粗さはある(low)。
