### 3-A1 (high) ベイク再生だけがレターボックスされ、12点キャリブレーションが崩れる

**場所**: `CornerCast/Scenes/ExternalSceneDelegate.swift:69` / `CornerCast/UI/TransportView.swift:83-84` / `CornerCast/Scenes/ExternalDisplayManager.swift:56-60`

出力経路が2本あり、**正規化座標(0,0)-(1,1)が物理パネルのどこに写るかが一致していない。**

- **リアルタイム**: `canvasSize = screen.currentMode.size`(パネルのネイティブ解像度そのもの)を採り、`metalLayer.drawableSize = renderSize`、`CIContext` は `composed.extent` 全体を drawable へ描く。正規化(0,0)-(1,1)は**パネル全面**に一致する(軸別の異方スケール、アスペクト非保存)。
- **ベイク再生**: 書き出しサイズは `TransportView.swift:83-84` の confirmationDialog で 1920×1080 か 3840×2160 の**16:9固定**。その動画を `AVPlayerLayer` が

```swift
playerLayer.videoGravity = .resizeAspect   // ExternalSceneDelegate.swift:69
```

で表示する。`videoGravity` への代入はリポジトリ全体でこの1件のみ(`.resize` / `.resizeAspectFill` は0件)。

`displayState.resolution` を読む箇所はリポジトリ全体で `EditorView.swift:155` のツールバー表示だけで、書き出しには一切渡らない。

**何が起きるか**

1920×1200(WUXGA)プロジェクタに接続し、リアルタイムモードで12点を部屋の角にぴったり合わせる。「この設定で書き出し」→ 1080p を選択 →「ベイク再生に切替」。投影は上下に黒帯を出し、映像全体が中央へ圧縮される。両写像を Python で再実装した実測値:

| パネル | ベイク動画 | 最大ずれ | パネル高比 |
|---|---|---|---|
| 1920×1200 | 1920×1080 | 60px | 5.0% |
| 1280×800 | 1920×1080 | 40px | 5.0% |
| 1920×1200 | 3840×2160 | 60px | 5.0% |
| 1024×768 (4:3) | 1920×1080 | 96px | 12.5% |
| 1920×1080 (対照) | 1920×1080 | 0px | 0% |

横方向(x)はどの組み合わせでも 0px。**16:9パネルでは症状がゼロなので、開発機では再現しない。**

悪いのは復旧手段が無いことだ。`startBakedPlayback` は `.bakedVideo` しか受け付けず、テストパターンはリアルタイム経路専用なので、**ベイク表示を見ながらの再キャリブレーションは構造的に不可能**。`BakeExporter.isStale` は `calibrationFingerprint` しか比較せず、解像度・アスペクトを見る箇所はゼロなので警告も出ない。`Quad.clamped` が全ドラッグ入口で 0-1 にクランプするため、「リアルタイム側で quad を広げて letterbox を先回り補正する」回避策も封じられている。

**要件との関係**: `docs/01:300` の M2.5 受け入れ条件「書き出したベイク動画が `AVPlayer` 再生のみで正しく3面にフィットし、**リアルタイムモードと同一の見た目になる**」に直接違反する。F-BAKE-2 / N-THERM-1 がベイク再生を長時間投影の既定と定めているため、**最も長く使われるモードが最も狂う**。

**直し方**

1. **即効(1行)**: `playerLayer.videoGravity = .resize` にする。metalLayer 側と同じ「非等方でフレーム全面に伸ばす」挙動になり、異方アフィンとワープのホモグラフィが合成されて4点対応が保存されるため、リアルタイムと幾何が厳密に一致する。
2. **本筋**: ベイク解像度を `displayState.resolution` から導出し(未接続時のみ 1920×1080 にフォールバック)、ダイアログは「パネル等倍 / 半分」等の倍率選択にする。ただし F-BAKE-4 が「1080p/4K を選択できる」を要求しているので、要件側の調整が要る。
3. `BakeRecord` は `outputWidth/Height` を持っているので、再生時にパネルのアスペクトと食い違うレコードには `ContentPickerView` で警告を出す。
4. 「同一の正規化点がリアルタイムとベイクで同一パネル画素へ写る」を、両写像を純関数に切り出したユニットテストで固定する。現行の `ProFeatureTests` / `FrameComposerTests` は extent しか見ておらず(2巡目 2-C1)、この不一致を検出できない。

**A/B の割れ**: B は「純正 Multiport 経由では出力が1080pにネゴシエートされ、対象構成の相当部分が免疫を持つ」(docs/01:276 R8)として medium を主張した。これは正しい留保だが、**免疫が効くかどうかは実機のネゴシエーション結果でしか決まらない**。本報告は「該当機では100%再現・恒久的・アプリ内に復旧手段なし・修正は1行」を重く見て high とする。**決着方法**: 16:10 のモバイルプロジェクタ(WXGA/WUXGA)を1台つないで `UIScreen.currentMode.size` をログに出す。それが 1920×1200 を返せば確定、1920×1080 を返せばその接続構成では無症状。

### 3-A2 (high) ガイドPNG生成がドラッグごとに同期実行される

**場所**: `CornerCast/UI/CropEditorView.swift:56-58`, `:189-203` / `CornerCast/Engine/CropGuideExporter.swift:9-18`

```swift
.onChange(of: viewModel.preset.calibrationFingerprint) { _, _ in
    prepareGuide()          // CropEditorView.swift:56-58
}
```

`calibrationFingerprint`(`Models.swift:241-265` → `configFingerprint:267-269`)は crop を `%.6f` で含む。`moveGesture` / `resizeGesture` の `onChanged` は毎イベント `setCrop` を呼び(`MappingViewModel.swift:139-143`、クランプのみで間引きも同値判定も無い)、`preset` が変わると fingerprint が変わり、onChange が発火する。`prepareGuide()` は **MainActor 上で同期に** `UIGraphicsImageRenderer(1920×1080, scale=1)` のラスタライズ → `image.pngData()` → `data.write(to:options:.atomic)` を実行する。`Task` も `detached` もデバウンスも無い。

**何が起きるか**

本コンテナで PIL/zlib により独立に再現した実測値:

| 処理 | 実測 |
|---|---|
| PNG encode + atomic write (1920×1080) | 40.5–40.8 ms/回、出力 8.5–9 KB |
| 同 + fsync | 45.7 ms |
| ラスタライズのみ | 8.8 ms |
| 60fps ドラッグ中の1フレーム予算 | 16.7 ms |

iPad の ImageIO はこれより速いはずだが、加えて毎回 1920×1080 の CPU ビットマップ(約8MB)を確保・全面塗り・テキスト描画するため、**ドラッグ1イベントあたり数十ms級であることは動かない**。UIKit のタッチ合体があるので完全停止ではなく「20fps程度でしか指に追従しない」形になる。

指摘者が見落としていた増悪要因がある。`OutputRenderer.swift:58` は `link.add(to: .main, forMode: .common)` で、**投影出力の CADisplayLink がメインランループ上にある**。`ExternalDisplayManager.swift:164-172` の realtime 経路はクロップ編集シート中もレンダラを止めない。したがって40-50msのブロックは編集UIだけでなく**投影フレームも落とす**。(なお `ExternalDisplayManager.swift:39` の「バックグラウンドの CADisplayLink スレッド」というコメントは `add(to:.main)` と矛盾し事実に反する。1巡目「確認したが問題なかったこと」でも同じコメントの誤りが指摘されている。)

**直し方**

`prepareGuide()` を `onChange` から外す。ShareLink を「ボタンを押した瞬間に生成する」形(Button + 遅延生成、または `Transferable` で要求時生成)に変えるか、シート離脱時のみに寄せる。`onChange` を残すなら `Task.detached` + 300ms デバウンスにし、最低限 MainActor から追い出す。数行で済む。

**同時に確認したが、指摘としては成立しなかった点**(記録のため):

- **不透明PNGで「下絵に使えない」** — 事実部分(`format.opaque = true` と全面黒塗り)は本物だが、帰結は支持されない。全面黒は「どの面にも割り当てられていない=投影されない領域」を示す情報そのもので、既定クロップは右1/3を捨てるためこの黒には意味がある。AI生成の参照画像は不透明が正しい入力形式で、動画編集側の不透明度調整も標準操作。
- **ワークフローがどこにも書かれていない** — grep 結果(`docs/01:105`、`docs/01:275`、`README.md:22` のみ。`docs/02`・`04`・`05`・`06` と `HelpView.swift` は0ヒット)は事実だが、出力PNG自体が `CropGuideExporter.swift:46-60` で各矩形に面名+正規化座標を焼き込む自己文書化された成果物であり、low 相当。
- **1920×1080固定** — ガイドの中身は全て正規化座標由来なので、4K や 21:9 のタイムラインに置いて枠に合わせて伸ばしても各矩形の境界は正規化位置のまま厳密に一致する(軸別の異方スケールはアフィンで直線と共有頂点を保存する)。1巡目のキャンバス16:9固定の項および2巡目 B6 と同じ論法で、幾何は壊れない。

**A/B の割れ**: B は「対象は F-CROP-2/3(いずれも優先度 S)の画面で、データ損失も機能不全も無い体感劣化」として medium を主張した。本報告は**投影フレームまで落とす**点(A・B とも事実として認めている)を重く見て high とする。**決着方法**: 実機でクロップ編集シートを開いたまま矩形をドラッグし、投影側のフレームレートを見る。

### 3-A3 (medium) 頂点リンクの伝播が1ホップ止まり

**場所**: `CornerCast/State/MappingViewModel.swift:320-328`

```swift
private func resolveLinks(changed ref: CornerLink.CornerRef, to p: CGPoint) {
    for link in preset.links where link.enabled {
        if link.a == ref {
            preset.surfaces[link.b.surface]?.quad[link.b.corner] = p
        } else if link.b == ref {
            preset.surfaces[link.a.surface]?.quad[link.a.corner] = p
        }
    }
}
```

部屋のコーナーで左壁・正面壁・床が交わる点は、モデル上 `leftWall.bottomRight` / `frontWall.bottomLeft` / `floor.topLeft` の3頂点で表され、`links[1]` と `links[2]` の2本で**鎖状**に繋がれている(`Models.swift:377-380`)。ところが `resolveLinks` は「今動かした頂点 ref を直接含むリンク」しか見ず、推移閉包を取らない。伝播先がさらに別のリンクの端点であっても再帰しない。

**何が起きるか**

同じ述語を Python で再実装して実測(既定の4リンク・全ON、3点を一致させた状態から):

```
初期(3点一致): LW.br=(0.33,0.65) FW.bl=(0.33,0.65) FL.tl=(0.33,0.65)
floor.topLeft ドラッグ後:          LW.br=(0.33,0.65) FW.bl=(0.30,0.72) FL.tl=(0.30,0.72)  ← LW.br 取り残し
leftWall.bottomRight ドラッグ後:   LW.br=(0.31,0.66) FW.bl=(0.31,0.66) FL.tl=(0.33,0.65)  ← FL.tl 取り残し
frontWall.bottomLeft ドラッグ後:   3点とも (0.31,0.66)                                     ← 正しい
```

**鎖の中央を動かせば正しく、両端を動かすと反対端が置き去りになる**という非対称性が生じる。ユーザーは「リンクをONにしたのだから継ぎ目は構造的に守られている」と信じているので、ズレを疑わずに動かし続け、動かすほど乖離が広がる。しかも正面壁側を動かしたときは正しく3点が動くため、「たまにズレる」という追いにくい症状になる。

`Models.swift:191` が「頂点リンク(F-WARP-5): a と b の頂点は常に同一座標に保つ」と**無条件に宣言している**ので、これは不変条件そのものの破れである。1ホップ限定を正当化するコメント・設計記述はリポジトリ全体に存在しない。

`move()` を呼ぶ全経路(`SimpleSetupView.swift:347` / `MeshCanvasView.swift:549` / `InspectorView.swift:261` / nudge 経由の十字キー / `ControlHub.swift:132` の OSC / `:185` の MIDI CC20/21)はいずれも `resolveLinks` を通る。

既存テスト `ViewModelTests.swift:74, 88, 101, 111` はすべて `links[0]`(単独リンク)で、`links[1]`/`links[2]` を同時に有効化した3点鎖のテストは1件も無い。

**申告より過小だった点**: `setLink`(`:330-341`)の吸着も同じ1ホップで鎖を考慮しない。トグル順を `links[2]` → `links[1]` にすると、**有効化した直後の時点で既に**3点が割れる(実測)。

**直し方**

`resolveLinks` を推移閉包にする。訪問済み集合を持つワークリストで、伝播先の頂点を新たな ref として再帰的にリンクを辿り、固定点に達するまで回す(リンクは高々4本なので計算量は問題にならない)。自己ループと循環リンクは訪問済み集合で止める。テストとして「links を全てONにし、鎖の3端すべてについて、どの端を動かしても3頂点が一致し続ける」ことを固定する。`setLink` も同じ閉包を通す。

**申告の重大な事実誤り(記録のため)**: 元の指摘は「かんたんセットアップの step3 で床の左上を動かした瞬間に左壁の右下だけが置き去りになる。step3 の画面は床の輪郭しか描かないため、割れたことがその場では見えない」としていたが、**この経路では起こり得ない**。`SimpleSetupView` への唯一の入口は `WelcomeView.swift:67-69` のカードタップで、必ず先に `apply(template: .cornerCockpit)` が走る。`makeDefault()` の4リンクは全て `enabled: false`(`Models.swift:376,378,380,382`。`DomainTests.swift:128` が明示的に固定している)。`setLink` の呼び出し元はアプリ全体で `InspectorView.swift:334` のトグル1箇所のみで、`SimpleSetupView` は一切呼ばない。したがってかんたんセットアップ中は完全な no-op である。また `MeshCanvasView` は3面の輪郭と12個のハンドルを常時描くため、リンクを ON にできる唯一の画面では割れが手元でも見える。**発火にはプロ用 Inspector で `links[1]` と `links[2]` を明示的に ON にするオプトイン操作が要る**ため medium。

### 3-A4 (medium) OSC引数パーサが未対応型タグでオフセットを進めない

**場所**: `CornerCast/Engine/Control/ControlHub.swift:313-318`

```swift
case "i":
    guard let bits = readUInt32BE(bytes, offset) else { return nil }
    floats.append(Float(Int32(bitPattern: bits)))
    offset += 4
default:
    // 未対応型タグはスキップ(引数長が不明なため読み飛ばさず無視する)
    continue
```

Swift の `switch` 内 `continue` は囲む `for` に作用するため、**f / i 以外の型タグでは offset が据え置かれる**。しかし OSC 1.0 のコア型のうち s(string)・b(blob)・h(int64)・d(double)・t(timetag) はいずれもバイト列を消費するため、これらが引数列に1つでも混ざると以降の f / i が**全て別のバイト位置から読まれる**。

**何が起きるか**

parse を Python に逐語移植して実測:

```
,sff (label="hi", 0.1, 0.2) → [4.4012455620345093e+24, 0.10000000149011612]   正: [0.1, 0.2]
,bff (blob deadbeef)        → [5.605193857299268e-45, -6.259853398707798e+18]
,hff (int64)                → [0.0, 9.8e-45]
,Tf                         → [1.5]   (0バイト型なので偶然一致)
,ff  (対照)                 → [0.1, 0.2]   正常
```

読み出し自体は `readUInt32BE` の範囲チェックを通る(スキップされる型は必ず4バイト以上を占めるため、読み位置は常に「本来より手前」にずれる)ので **nil にはならない**。パースは「成功」してアドレスも `floats.count` も正しいまま `apply(osc:)` へ渡り、`guard floats.count >= 2`(`:129`)も通過し、`clamp`(`:220`)が化けた巨大値を **0 または 1 という合法な極値**に丸めるため、どの層でも異常として検出されない。結果、`/cc/corner/leftWall/tl` に `,sff` で送ると左壁の左上頂点がキャンバス右端へ飛ぶ。エラーもログも出ない。

**直し方**

**申告の誤り2点(機序自体は無傷)**:

### 3-A5 (medium) バインド失敗を観測せず、緑の「OSC受信中」を出し続ける

**場所**: `CornerCast/Engine/Control/ControlHub.swift:67-73`, `:93` / `:243-251` / `CornerCast/UI/ControlSettingsView.swift:88-92`

```swift

isRunning = oscServer != nil                    // :93

    stop()

    listener.newConnectionHandler = { ... }
    listener.start(queue: queue)                // :249 ← バインド結果は返さない
    self.listener = listener
}
```

`OSCServer.start()` が実際にやるのは `NWListener` の**生成**と `listener.start(queue:)` の呼び出しだけで、これらは同期的にバインド結果を返さない。ポート衝突(EADDRINUSE)等の実際の失敗は `stateUpdateHandler` に `.failed` として非同期に届くが、**そのハンドラはリポジトリ全体で0件**(`grep -rn "stateUpdateHandler" CornerCast/` を実行して確認)。

さらに `ControlHub` は `ObservableObject` でも `@Observable` でもなく `isRunning` は素の格納プロパティで、`ControlSettingsView` は `@State` へ `onAppear`(`:141`)と `apply()`(`:148`)でコピーするだけ。**仮に `.failed` を観測しても UI へ伝える経路が無い**という二重の断絶がある。

補強材料として、`listener.start(queue:)` は非 throwing で、そもそも同期的にバインド結果を返せない型をしている。`NWListener(using:on:)` が throw するのはオブジェクト生成時に拒否される場合で、`.udp` かつ `:59` で 1024...65535 にクランプ済みのポートではまず起きない。つまり **`:67-72` の do/catch は事実上デッドコードで、`isRunning` は `oscEnabled` のミラーに退化している**(申告より一歩強い)。

**何が起きるか**

別のアプリが UDP 8000 を掴んでいる状態で OSC を有効化すると、設定画面は緑の「OSC受信中」を表示するが、実際にはリスナーはバインドできていない。ユーザーはコントローラ側の設定・Wi-Fi・ケーブルを延々と疑うことになり、アプリ側が「受信中」と断言しているためアプリを疑わない。

同一 UDP ポートへの二重 bind が EADDRINUSE(errno 98)になり `SO_REUSEADDR` だけでは通らないことは Python で実測確認した。Network.framework は `allowLocalEndpointReuse` 既定 false なので衝突は実在し、結果が非同期に届くだけである。

**直し方**

`OSCServer` に `var onStateChange: (@Sendable (NWListener.State) -> Void)?` を設け、`listener.stateUpdateHandler` で `.ready` / `.failed` / `.cancelled` を `ControlHub` へ通知する。`isRunning` は `.ready` を受け取ったときだけ true にし、`.failed` のときはエラー内容を保持して「ポート8000を確保できませんでした(使用中)」と**理由付きで**表示する。`ControlHub` を `@Observable` 化し、`ControlSettingsView` のローカルコピーをやめる。**この最後の一手までやらないと修正の意味がない。**

**申告のうち成立しない failure mode 2点**:

- **権限拒否は起きない。** `ControlHub:59` と `ControlSettingsView:20` が 1024...65535 に制限するので、特権ポートに到達する経路が構造的に無い。
- **Wi-Fi 切断では `.failed` にならない。** ワイルドカードアドレスにバインドする本コードではループバックが常在するのでバインドは維持され、状態は `.ready` のまま。正しく実装しても Wi-Fi 断は緑のままである。

**併せて見つかった補強材料(実機でしか確定できない)**: `start()` は先に `stop()` → `listener.cancel()` を呼ぶが cancel は非同期で、その直後に同一ポートで新 `NWListener` を生成する。**「適用」を続けて2回押すだけで自己衝突しうる**。

**A/B の割れ**: B は「発火条件が特定 UDP ポートの衝突1つに絞られ、帰結は診断可能性の低下のみ。しかも OSC の動作確認でユーザーが見るのはフェーダを動かしたときの投影であって緑丸ではなく、IP違い・サブネット違いでは修正後も同じく緑になる」として low を主張した。この批判はかなり強い。本報告は「要求されていない表示が根拠のない断定をしている」構造を欠陥と見て medium に置くが、**low との境界であることは認める**。

### 3-A6 (low) ベイク進捗ポーラが1周目で break し得る

**場所**: `CornerCast/Engine/BakeExporter.swift:142-150`, `:158` / `CornerCast/UI/TransportView.swift:130`

```swift
let progressPoller = Task { [weak self, weak export] in
    while !Task.isCancelled {
        guard let export else { break }
        self?.progressHandler?(Double(export.progress))
        // .waiting / .exporting の間だけ継続。完了・失敗・キャンセルで抜ける。
        guard export.status == .waiting || export.status == .exporting else { break }
        try? await Task.sleep(nanoseconds: 250_000_000)

}
```

ループ本体は progressHandler を**先に**呼び(このとき 0.0)、その直後に status を検査する。`AVAssetExportSession.status` の初期値は `.unknown` で、これは guard のどちらの条件にも当たらないため、その窓に入ると**1周目で break してループが永久に終わる**。以後 `:175` の `progressHandler?(1.0)` まで一度も進捗が更新されない。

**申告の主因は誤り。** 「ポーラ Task が `exportAsynchronously` より先に別コアで走る」はほぼ起こらない。`:142` から `:158` の間に実行されるのは defer 登録と `withCheckedThrowingContinuation` のみで、後者は body クロージャを現在スレッド上で同期実行するため、親は数百ナノ秒で `exportAsynchronously` に到達する。一方、非構造化 Task の enqueue → 他コアでの実行開始はワーカー起床を伴い µs オーダー。

残るのは「`exportAsynchronously` に入ったが status がまだ `.unknown`」という経路だけで、これは AVFoundation が status を同期的に `.waiting` へ倒すかという実装詳細に完全に依存する。**倒すなら発火率は実質 0、倒さないなら実質 100% で全書き出しが 0% 固定になる。**つまりこれは「レースなので起きたり起きなかったり」ではなく、**OS 実装で決まる二値挙動に近い。この環境では AVFoundation を実行できないため、どちらの regime かは判定できない。**

**何が起きるか**: 90分の4K動画をベイク書き出しすると、`exportOverlay` が「書き出し中… 0%」のまま数十分固まる。ユーザーは失敗したと判断してキャンセルを押す。以後の被害(残骸 mp4 が index.json に載らないゴミとして残る)は2巡目 B1 の欠陥であって本項固有の害ではない。

**直し方**: (1) 終了条件を反転させ `if export.status == .completed || .failed || .cancelled { break }` として `.unknown` を継続扱いにする。または guard を sleep の後ろへ移す。(2) より確実には、ポーラの起動を `exportAsynchronously` の呼び出し後へ移す。(3) 0% のまま数秒経ったら「準備中…」を出す。(4) ついでに `currentExport` は非分離クラスの var を MainActor(`cancel()`)と別実行文脈(`export()`)の両方から触っているので、`@MainActor` 化かアクター保護を入れる。

修正は1行。**議論より直す方が安い**類の low である。

## 3巡を終えての所見

### このアプリは「やりたいこと」にどこまで届いているか

3巡・約60件の指摘を通して、CornerCast の状態はかなりはっきりした。

**設計は正しい。** 座標変換を `CoordinateMapper` 1箇所に集約する規約、プレビュー・リアルタイム・ベイクの3経路が同じ `FrameComposer` を通す構造、ベイクモードを長時間運用の根本策に据えた熱設計。これらは「この種のアプリで最も壊れやすい部分」を的確に押さえており、3巡かけても設計そのものへの反証は1件も立たなかった。要件定義書(`docs/01`)の Must はほぼ全て「コードとして書かれている」段階に到達しており、CI は3ジョブグリーンで、同梱サンプルは実ビルドで動くことが決着している。

**壊れているのは、設計と実装の間の「一致の担保」である。** 3巡で見つかった欠陥は、性質別にきれいに3層へ分かれた。

| 巡 | 型 | 代表例 |
|---|---|---|
| 1巡目 | **主経路の外に出ると無言で壊れる** | 未接続時に再生が全無反応(#1)、ベイク再生中のコンテンツ切替(#2) |
| 2巡目 | **入口が無防備で、テストが何も守っていない** | importJSON がゲートを迂回(2-A3/A4/A5)、恒真アサーション(2-C1) |
| 3巡目 | **同じものを二度書いた場所が全部ずれている** | 出力写像2本の不一致(3-A1)、リンク伝播1ホップ(3-A3)、識別色5箇所(B5) |

3層は独立ではなく、同じ根から出ている。**このコードベースは不変条件を「コメントで宣言する」ことでしか担保していない。** `EditorPreviewRenderer.swift:5-7` は「プレビューと実際の投影結果が必ず一致することを**構造的に保証する**」と書き、`docs/02:154` は「ベイク結果とリアルタイム表示が**必ず一致する**」と書き、`Models.swift:191` は「a と b の頂点は**常に**同一座標に保つ」と書く。**その3つとも、今日の実装では成立していない**(それぞれ1巡目 #4、3巡目 3-A1、3巡目 3-A3)。そして2巡目 2-C1 が見つけたとおり、これらを検査するテストは1行も無い。

blocker は3巡を通してゼロ。データを永久に失う経路も、クラッシュも、要件の全面未達も無い。**この製品は「動く」段階には確実に到達している。**

### 残る最大のリスク

**「正しく合わせた12点が、ユーザーの操作ミスなしに崩れる」経路が塞がれていないこと。**

キャリブレーションはこのアプリで唯一、ユーザーが時間と労力を投じて作る資産である。暗い部屋で iPad を持って壁と画面を往復しながら12点を詰める作業には、おそらく数十分かかる。それが無言で崩れると、ユーザーは原因を特定できず、やり直す以外の手段を持たない。

3巡で見つかったこの型の欠陥は3件ある。

1. **3-A1(high)** — 非16:9パネルでベイク再生に切り替えた瞬間、パネル高の5%(4:3機では12.5%)ずれる。**アプリ内に復旧手段も警告も無い**(ベイク再生中はテストパターンを出せないため、合わせ直すことすら構造的に不可能)。修正は1行。
2. **3-A3(medium)** — リンクを ON にした状態で鎖の端を動かすと反対端が置き去りになる。「リンクは守ってくれる」という信頼の下で悪化し続ける。
3. **1巡目 #3(high)** — 編集ロック中に「全てリセット」で12点が初期値に戻る。

これらに共通するのは、**壊れたことがユーザーに伝わらない**点である。1巡目の総評が「無言で誤った状態を維持する」と書いた性質は、3巡を経ても消えていない。

次点のリスクは**検証基盤の空白**である。2巡目 2-C1 の恒真テストと 2-C3(Engine 層6ファイル+Scenes 層がテスト0行)を直さない限り、上記3件を修正しても再発を止める番人がいない。3-A1 も 3-A3 も、「不変条件を純関数に切り出してユニットテストで固定する」という同じ処方に収束する。

### 実機検証で最初に確かめるべきこと

このレビューは3巡とも一度も実機に触れていない。以下は**優先順**で、いずれも短時間で済み、判定を大きく動かす。

1. **非16:9プロジェクタを1台つなぎ、`UIScreen.currentMode.size` の実値をログに出す。**(3-A1 の発火可否 / B判定者が唯一の免罪符として挙げた「1080p ネゴシエーション」がどのくらい効くか)。同じ接続で12点を合わせ→ベイク→再生に切り替え、ずれを実測する。**これ一つで high 1件の運命が決まる。**
2. **ベイク書き出しを1本走らせ、進捗バーが 0% に張り付くか見る。**(3-A6。`AVAssetExportSession.status` が同期的に `.waiting` へ倒れるかは OS 実装依存で、**発火率は 0% か 100% のどちらかに近い**。この環境では判定不能)。
3. **クロップ編集シートを開いたまま矩形をドラッグし、投影側のフレームレートを見る。**(3-A2。実測40ms級のブロックが `.main` ランループ上の CADisplayLink をどれだけ落とすか)。
4. **メッシュを ON にして格子シームが目視できるか**(1巡目 #6)**、feather を 0.1 にして継ぎ目に暗帯が出るか**(B1)。どちらも Core Image の実行が必要で、この環境では原理的に判定できない。暗室で1回見れば両方同時に片付く。
5. **4Kソース×3面ワープの実効fpsを計測する。**(`docs/01:300` の M2「冒頭に実機性能計測スパイク」/ `docs/04:36` の「性能目標は現時点で仮説」)。3巡を通して未着手のまま残っており、サーマル関連の全判断(B4/B6/B7)がここに依存している。

そして修正の順序としては、**まず 2巡目 2-C1(恒真テスト)を直してから 3-A1 と 3-A3 に着手する**ことを勧める。この2件はどちらも「宣言された不変条件が守られていない」型なので、テストが機能する状態にしてから直さないと、直したこと自体を確認できない。
